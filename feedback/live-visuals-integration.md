# Field Feedback — Authorship Meter, from the Live Audio-Reactive Visuals integration

**Date:** 2026-08-08
**Framework version exercised:** spec v1.1, component v1.1, the "Assessment & Integration Playbook"
**Subject project:** [Live Audio-Reactive Visuals](https://github.com/luispsalas/live-visuals) — a browser VJ instrument (code)
**Method used:** Part A assessment (git history + author's account), `llm-assisted`, author-confirmed

This is one real end-to-end pass: assess a project from its history, produce a declaration,
and publish it. It surfaced a few things worth folding back into the framework. Nothing here
is a blocker — the format did its job. Two fixes were applied to this repo during the pass
(noted below); the rest are recommendations.

---

## What worked well (keep it)

- **The `compact` / `open` attributes are exactly the right primitive.** A README needs the
  summary card (band + human/AI bar + provenance); the interactive page needs the full
  breakdown. `compact` gave the first and the default gave the second from the *same*
  declaration, no duplication. This is the single most useful part of the component for
  real embedding.
- **Calibration rules 2 and 3 did real work.** "Volume is not leadership" (rule 2) and
  "editing does not lower Production" (rule 3) are what kept Production at level 4 instead of
  5 for a project where the model wrote ~all the code under close human direction. Without
  those two rules the assessment would have over-stated AI authorship. They are the load-
  bearing rules; keep them prominent.
- **The "does the band match the intuitive story?" check (A.6) is a good final gate.** It
  caught nothing wrong here, but it's the step that makes the arithmetic accountable to the
  narrative instead of the other way round. Worth keeping as a required step, not a footnote.
- **Provenance always visible (method / declarer / assessed date).** Because the assessing
  model was *also the producing model*, surfacing `llm-assisted` + declarer + date up front
  is what makes the declaration honest rather than self-serving. This design choice matters
  most in exactly the common case (see friction #5).
- **`subject.url` vs `subject.source` split** mapped cleanly: `url` → the live app, `source`
  → the repo, and "How this was assessed ↗" pointing at `source` is the right default.

## Friction and issues found

### 1. "About this scale" pointed to the demo page, not the framework docs — **fixed this pass**
`METER_HOME` (the "About this scale ↗" link target) was `https://luispsalas.github.io/authorship-meter/`
— the Pages demo, which shows *example meters* but doesn't explain the framework. A reader who
clicks "About this scale" wants the definition of the 1–5 scale, which lives in `SPEC.md` in
the repo, not the gallery.

- **Applied:** `METER_HOME` → `https://github.com/luispsalas/authorship-meter` (commit `5f12ced`).
- **Recommendation for upstream:** either keep it pointing at the repo, or point it more
  precisely at `SPEC.md` (the actual scale definition). Consider whether "About this scale"
  and "How this was assessed" should be *separately* configurable — the former is a framework
  link (same for everyone), the latter is per-declaration; a project embedding the meter can't
  currently override the framework link, which is probably correct, but the target it ships
  with should be the docs, not the demo.

### 2. Linked component + Pages caching = stale JS after any component change — **mitigated this pass**
Because the playbook recommends *linking* the component (not vendoring) while pre-1.0, every
consumer loads `authorship-meter.js` from Pages, which serves it with a short `max-age`. After
the `METER_HOME` fix above, a browser kept rendering the old link until a hard refresh — the
origin was correct, the client was cached.

- **Applied:** added a `?v=20260808` query to the script `src` on the embedding pages
  (commit `0733ce1`), so bumping it forces a fresh fetch.
- **Recommendation for upstream:** document the cache-busting expectation in the playbook's
  "Link vs. vendor" section (B.4). Better still, ship **versioned filenames**
  (`authorship-meter-1.1.1.js`) alongside the unversioned one, so a consumer can pin a version
  and get cache-safety for free. The current model silently propagates *and* silently caches,
  which is the worst of both — a component fix looks unshipped to anyone with a warm cache.

### 3. The widget can't render in a README, and the static-image workaround goes stale
The playbook already says this (B.1), but the downstream cost is real: to show the meter on a
README you render it to a static image, which then **drifts from the declaration** and must be
regenerated by hand on every re-assessment. We captured a compact PNG with headless Chrome and
noted "regenerate on re-assessment" in the project backlog, but that's a manual coupling the
framework could own.

- **Recommendation for upstream:** provide an official static-render path. Options, roughly in
  order of usefulness: (a) a documented headless-capture recipe in the playbook (so everyone
  does it the same way), (b) an SVG export mode on the component (SVG embeds in READMEs without
  scripts and stays crisp), or (c) a shields.io-style badge endpoint that renders
  `band + %AI` live from a declaration URL — that one solves staleness entirely because it
  reads the JSON at request time.

### 4. Hosting the live page is awkward for built (non-static) apps
Part B.2 assumes a static passthrough dir (`public/`). For a Vite app, dropping
`authorship.html` in `public/` means it **ships inside the app's own deployment**, which was
not wanted here (the app and its authorship page are different concerns). We resolved it by
hosting the declaration on the **meter's own site** under `declarations/<project>.{html,json}`
and linking to it from the project's README.

- **Recommendation for upstream:** formalize a `declarations/` convention on the meter site as
  a first-class hosting option in the playbook — "if you don't want the declaration inside your
  app's build, host it here." It worked cleanly and keeps built apps untouched. This pass added
  `declarations/live-visuals.{html,json}` as a working example of the pattern.

### 5. The assessing model is often the *producing* model — say so explicitly
Here, the model that wrote ~all the code also produced the declaration. The playbook's
`llm-assisted` + "hand to the human to confirm or contest" is exactly the right safeguard, and
it worked — but the playbook frames the LLM as an assessor reading a repo it didn't write. In
agentic coding the more common case is the assessor *is* the author.

- **Recommendation for upstream:** add one line to Part A calling this case out by name, and
  reinforce that the human sign-off is doing more work there (the model has a bias toward
  narrating its own contribution as larger and cleaner than it was). Nothing structural to
  change — just name the common case.

### 6. `subject.version` semantics during integration are ambiguous
The commit that *adds* the declaration is not the state being *assessed*. We pinned
`subject.version` to the assessed commit (`09c047c`) rather than letting it drift to the commit
that added the meter files.

- **Recommendation for upstream:** the A.6 checklist item for `subject.version` should say
  explicitly "the commit of the *assessed work state*, not the commit that adds the
  declaration" — otherwise every integration bumps it by one for no real change.

### 7. The bare declaration page is context-poor
`declarations/<project>.html` renders the meter and a back-link, but on its own it doesn't tell
a first-time visitor what the project *is*. The author flagged this directly.

- **Recommendation for upstream:** the Part C `authorship.html` template could include a one-line
  project description and links to *both* the artifact and the framework, so a shared
  declaration URL stands on its own.

---

## Suggested priority for the framework

1. **Ship the `METER_HOME` = repo/SPEC target** (done here; adopt upstream). Lowest effort,
   fixes a wrong-destination link every meter shows.
2. **Address caching** — versioned filenames or a documented `?v=` convention. Cheap, and it's
   the difference between a component fix shipping or silently not.
3. **An official static-render/badge path** — the biggest ergonomic win for README embedding,
   and the only thing that kills the image-staleness coupling.
4. **Doc clarifications** — `subject.version` meaning (#6), the assessor-is-author case (#5),
   the `declarations/` hosting pattern (#4). Words, not code.
